Registering a service provider

(Naming Convention) The File Name: Create a plain text 
file inside the services/ directory. The name of the 
file must be the Fully-Qualified Class Name (FQCN) of
the interface or abstract class you are implementing.
The File Content: Inside this file, list the FQCN of 
your implementation class(es), with each implementation 
on a new line. Then, the service provider must be made
available to the consumer's class path (or module path, 
depending on the application).




In traditional: class-path based SPI

where explicitly invokes ServiceLoader.load() on code: 
I.E., the registration only makes the provider discoverable 
through the SPI mechanism. Some piece of code must actually
consume the SPI, normally by invoking ServiceLoader.load() or 
another API that uses the same mechanism. Being a form of
runtime service discovery. 



Annotation processors: A Special Case

Annotation processors use the same SPI registration
mechanism, but the consumer of the SPI is not normally
application code.


META-INF/services/ 
└── javax.annotation.processing.Processor


META-ING/services/, declare the Providers(implementations)
disponíveis para cada SPI/services. So Registers 
RouterProcessor as an implementation of the Processor service
(declarative link) as a Service Provider to his Service Contract.
Without creating tight coupling between the consumer and the
concrete implementation. When a Java compilation is performed,
the annotation-processing infrastructure of the compiler 
discovers available Processor implementations using the
processor discovery mechanism. The compiler performs the
discovery on your behalf.

Therefore ServiceLoader.load() does not appear in your
application code because the compiler is the component
responsible for discovering and invoking the processor.

The two approaches nevertheless share the same fundamental
SPI idea: a service interface is associated with one or
more implementation classes through a declarative provider
configuration, allowing the implementation to be discovered
without a direct compile-time reference from the consumer.

Finally, this discovery mechanism should be distinguished
from the use of Reflection by the application itself. 
ServiceLoader performs dynamic provider discovery and 
instantiation internally, but the consumer does not have to
directly manipulate Class, Method, Constructor, or invoke
methods reflectively. In an annotation-processing setup, this
dynamic discovery occurs during compilation, while the code
generated by the processor can use ordinary statically 
compiled Java method calls at runtime. ^YOPgTFFg
